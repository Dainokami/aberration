# 大地图区块加载

2026-10-19，Godot 4.7.2。

## 使用

正常打开地图或启动试玩即可。TerrainBuilder 默认开启 `chunk_loading`；一次完整重建时，含地形的列数超过 16,384 自动采用区块加载。200×200、600×600 满地图均启用；小地图与大范围但内容很少的地图保留完整构建。

- 编辑器跟随正在编辑的 3D 视口相机。移动、固定视角、自由视角和缩放均更新加载范围。
- 游戏跟随玩家与主相机。视锥内的地形加边缘预载范围决定显示区块，玩家附近保证物理碰撞；出生、快速移动和重置优先补齐脚下。
- 每区块 8×8 格，即 16×16 米。离开视野时留一圈缓存避免边缘反复加载，继续远离后释放地形、碰撞、混合纹理和细节。
- 传送门、Boss 门及仍活动的怪物保留附近地面。远处不活动怪物暂停物理与攻击，回来恢复原实例、血量和刷新点存活计数。
- 宝箱状态、盖子姿态、采集状态、果实、破坏状态和被推走物件的位置按运行实例保持；宝箱掉落和已生成藤蔓在卸载期间暂停，回来继续。
- 地图数据始终完整。编辑远处未加载地块、撤销、重做及保存均作用于完整数据；再次到达时读取最新内容。

无需转换地图、重新绘制或改变地块 ID。排查时可关闭 TerrainBuilder 的 `chunk_loading` 并重新构建，恢复完整场景构建。

## 实测

本机 Apple M5 Pro。CPU 构建对比采用同一张200×200草/岩满地图，同一构建器与材质；启动时间只计算加入 TerrainBuilder 时的初始构建，不含资源导入、全地图文件读取和完整游戏 UI 初始化。

| 项目 | 完整构建 | 区块加载 |
| --- | ---: | ---: |
| 初始地形构建 | 约13.0秒 | 约68毫秒 |
| 固定36米正交相机稳定后区块 | 625 | 25 |
| 相同场景统计口径的子节点 | 202,846 | 4,912 |

600×600满地图初始约268毫秒、1个出生区块；同尺度相机稳定后工作区仍少于80个区块。快速转移到远处后旧区块会释放，并未逐步累积全图。

200×200实际混合生态生成约544毫秒；区块初建及处理完初始队列约239毫秒，9个区块、1,811个节点和3个附近物件。

最终暂存副本Metal Forward+实际游戏行走测试：帧时间中位数约17.2毫秒、P95约24.7毫秒，测试最大帧约33.5毫秒，单帧区块构建峰值约22.7毫秒。完整游戏启动约376毫秒。不同相机视野、资源缓存、物件密度与同时运行的测试会影响结果。

- `tests/editor_chunk_streaming_checks.gd`：实际插件鼠标输入、绘制撤销重做、独立细节画笔刷新/擦除、相机移动缩放、远处撤销、保存重新读取未加载内容。
- `tests/render_chunk_streaming.gd`：实际试玩场景、玩家连续跨区块行走、30秒刷怪、区域导航、怪物休眠/血量恢复、大半径活动怪物地面、重置和传送门；`--water`模式覆盖跨区块游泳和水体标签。

原分层地形、自由块、地形美术/接缝、编辑器V2、怪物、固定刷新点、游泳/Jolt碰撞、传送流程测试均通过。编辑器V2套件刻意保存非法目录产生两条预期错误，不能将其误记为新增失败。

提交前从 Git 暂存树导出无 `.godot` 缓存副本重新导入：51项区块检查、11项编辑器检查、11项Metal运行检查、2项水体检查与V2数据回归全部通过，控制台无新增错误；不借用用户未提交的地图、场景或私人配方。本文实测数字取自这轮最终副本验证。

运行入口（在项目目录，`GODOT_BIN`指定本机Godot可执行文件）：

```sh
"$GODOT_BIN" --headless --path . --script res://tests/test_chunk_streaming.gd
"$GODOT_BIN" --headless --editor --path . -- --test-stream-editor
"$GODOT_BIN" --path . --script res://tests/render_chunk_streaming.gd
"$GODOT_BIN" --headless --path . --script res://tests/render_chunk_streaming.gd -- --water
```

## 性能边界

此实现减少场景实例化与活动物理规模，完整 LevelData 仍在内存中；文件读取、世界生成算法、全地图校验和保存仍随地图数据量增长。它们并未全部变成后台任务。

区块采用约4毫秒构建预算，导航采用约2毫秒预算。构建分行、网格、收边和发布阶段执行，但不能中断 Godot 原生单次网格、物理注册或物件实例化调用，因此实测仍存在超过预算的帧，不能保证绝对无卡顿。

缩放到显示整张地图时，视锥要求的加载区块也会增加。大面积水体、极高层数、密集大型物件、超大手工刷怪半径或大量仍活动怪物可能进一步增大工作区；本次600×600验证覆盖地形加载与相机转移，未覆盖600满地图高密度长时间战斗。

休眠怪物保留轻量实例，已交互物件的少量状态及暂停掉落也会保留。运行状态保持于当前关卡会话，不构成新增跨会话存档系统。
